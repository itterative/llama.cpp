## The v1 build tree is unloadable (verified)

`build/` was configured and compiled 2026-09-17 10:59, i.e. ~7 h before the upgrade, and its
`libggml-hip.so` still `NEEDED`s the v1 SONAMEs:

```
$ LD_LIBRARY_PATH=$PWD/build/bin ldd build/bin/test-backend-ops | grep -i 'not found'
    libhipblas.so.2 => not found
    librocblas.so.4 => not found
    libamdhip64.so.6 => not found
```

So the loader-trap pin recipe cannot resurrect it - there is nothing to pin to. It needs a fresh
configure with the recorded line (the prefix is unchanged, so the flags are unchanged):

```sh
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_HIP=ON \
      -DGPU_TARGETS=gfx1201 -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++
```

One hazard for that rebuild: the upgrade ran `dnf remove compiler-rt18` and `dnf remove
libomp18` (tx 155/156) shortly after. If a HIP compile fails in an unfamiliar way, suspect those
before suspecting our flags.

**v1 cmake cache** (the tree is now unloadable, see above; reconfigure, do not
`cmake --build` against this):

```
CMAKE_BUILD_TYPE=Release   BUILD_SHARED_LIBS=ON   GGML_HIP=ON
GGML_HIP_GRAPHS=ON         GGML_HIP_MMQ_MFMA=ON   GGML_HIP_NO_VMM=ON

GGML_CUDA=OFF              CMAKE_CXX_COMPILER=/usr/lib64/ccache/c++
```

`AMDGPU_TARGETS` is not in the cache: auto-detected -> builds for the local gfx1201
only, which is fine here but means this binary is *not* a fat binary for the 4-GPU
box unless that box is also gfx1201.

Rebuild after any source or cmake change, and never trust a timestamp:

```sh
cd /home/sd/Repos/worktrees/llama.cpp/polished-quarry/llama.cpp
cmake --build build -j"$(nproc)"
```

## THE LOADER TRAP (this already produced two bogus results)

`LD_LIBRARY_PATH` on this box contains `/home/sd/lib` and `/home/sd/.local/lib64`,
and `~/.local/lib64` holds a **stale llama.cpp install from Sep 15** whose `libggml`
does not contain `ggml_dsv4_hc_*` (verified with `nm -D`, 0 matches). `BUILD_SHARED_LIBS`
means every binary in `build/bin` is dynamic with no rpath, so it resolves *that*
libggml unless told otherwise.

Consequence: running a benchmark without pinning the path measures two-day-old
installed code, not the working tree. It can also fail loudly instead:

```
test-backend-ops: symbol lookup error: undefined symbol: ggml_dsv4_hc_pre_gated
```

Always pin, and always confirm the resolution before believing a number:

```sh
export LD_LIBRARY_PATH=$PWD/build/bin
ldd build/bin/llama-bench | grep -E 'lib(ggml|llama)\.so\.0 '   # must say .../build/bin/
```

Verified: with the pin, both resolve to `.../polished-quarry/llama.cpp/build/bin/`;
without it, both resolve to `/home/sd/.local/lib64/`.

## Concurrency / cleanliness rules for this box

- one GPU, and it drives the display (DP/HDMI connectors present): a T1 run makes the
  box sluggish and can be timed out by nothing. Do not run perf measurements while a
  session is being used interactively, and never trust a run where something else was
  on the GPU - `rocm-smi --showmeminfo vram` "Used" should be near-idle before starting.
- `GGML_HIP_NO_VMM=ON` means VRAM fragmentation behaves differently than the CUDA
  default; peak-VRAM numbers from this box are not transferable to a VMM-enabled build.
